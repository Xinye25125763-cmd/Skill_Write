# skill-forge v1.4 优化需求文档

> 来源：《skill-forge vs skill-creator 对比报告》（2026-10-05）§5"应抄的作业"。
> 性质：需求定义文档，供下一轮工程计划（类似 v1.3 修改建议→逐项实现的流程）立项使用。
> 基线：v1.3 完整版（commit `80b0f81`），后端 214 项测试全绿。

---

## 1. 背景与总目标

对比 CatPaw 内置 skill-creator 后确认：skill-forge 在**生产侧**（无人值守、版本审计、自动修复、环境独立）已形成优势，但在**验证侧**存在三个盲区，共同指向同一个缺口——

> **现有五维验证证明"产物没坏"，但不能证明"产物好用"。**

| 盲区 | 现状 | 造成的真实损失 |
|---|---|---|
| 触发质量 | 装进宿主后触发准不准，零覆盖 | CatPaw 真实使用实验中发生"5→1 召回"塌缩：技能本身合格，但宿主不选它 |
| 结果稳定性 | 每用例只跑 1 次，按组汇总计数 | flaky 用例（重跑结果翻转）与恒过断言（不区分有无技能）都不暴露 |
| 主观质量 | 只有程序断言（text_contains 等） | 结构对但写得好不好，机器目前不评价 |

三项优化按价值排序立项：**R1 触发优化（P1）→ R2 方差分析（P2）→ R3 盲评对照（P2）**。

---

## 2. R1：Description 触发验证与优化（P1）

### 2.1 动机

技能的 description 是宿主选路的第一现场。skill-forge 生成的产物目前只验证内容（五维），description 只要求 frontmatter 存在。真实事故（5→1 召回）证明：**产物合格 ≠ 会被触发**。这是从"生产技能"到"技能被用起来"的最后一公里。

### 2.2 目标

- 导出收据新增第六维 `trigger`，与现有五维同模式：未运行如实 `not_run`，不粉饰。
- 触发不合格的产物**不阻塞导出**（与 eval 折算同语义：如实标注，由用户决定）。

### 2.3 需求明细

| ID | 需求 | 必要 |
|---|---|---|
| R1-1 | 触发用例生成：交付时自动生成触发用例集（默认 20 条），分两类——should-trigger（正例：真实用户口吻、含口语化/错别字/近义表达）与 should-not-trigger（负例：相邻领域、易混淆场景） | 是 |
| R1-2 | 触发判定执行：对每条用例模拟宿主选择行为——向模型呈现候选技能列表（目标技能 + 干扰项），判定目标技能是否被选中 | 是 |
| R1-3 | 触发评分：输出召回率（正例命中）、误触率（负例误选）、总体分；逐例结果入库（eval_run 体系内可查） | 是 |
| R1-4 | description 迭代优化：评分低于阈值（默认 0.85）时，把失败用例作为证据驱动模型改写 description，重评；**有界 ≤3 轮**（同修复纪律：no_progress / rounds / budget 三种停止原因入 meta） | 是 |
| R1-5 | 折算进导出收据：trigger 维度结论 + 证据写入 delivery/report.json；描述改写若发生，导出的必须是改写后的版本 | 是 |
| R1-6 | description 长度纪律：改写后 frontmatter description ≤1024 字符，超长视为该轮失败（有界停止信号之一） | 否（建议） |
| R1-7 | 触发用例集人工可改：用例以文件形态（如 trigger_cases.json）随版本冻结，用户可编辑后重跑 | 否（建议） |

### 2.4 验收标准

1. 交付一个 description 模糊的技能 → trigger 维度如实 failed，且证据列出具体失利用例；
2. 迭代优化后 description 变化、评分提升，产物内容文件不变（只有 frontmatter 变 → 新版本，符合不可变纪律）；
3. 迭代 3 轮无进展 → 如实停止并交付原 description（stopped_reason=no_progress 入报告）；
4. 导出收据中 trigger 维度与数据库逐例结果一致（对账）；
5. 单元测试覆盖：正/负例判定、评分计算、有界停止三信号、1024 字符边界。

### 2.5 非目标

- 不做宿主真实埋点回传（离线平台拿不到运行时数据，属宿主侧职责）；
- 不为特定宿主（CatPaw/ChatGPT）硬编码选择逻辑——模拟器只假设"模型按 description 选路"这一通用行为。

### 2.6 技术要点

- 复用 eval_run 框架：触发判定就是一类新 case（kind=trigger），评分器走模型调用；
- 干扰项来源：本项目内其他已交付技能的 description（真实混淆源），不足时用固定占位集；
- 成本控制：20 用例 × 判定 1 调用 + 优化 ≤3 轮，单版本触发验证预算上限约 25 次模型调用，进 budget 台账（stage_id=`trigger`，与 eval 同级）。

## 3. R2：评测方差分析（P2）

### 3.1 动机

当前评测每用例跑 1 次、按组汇总计数。两个被掩盖的风险：

- **flaky 用例**：同一用例重跑结果翻转，"passed" 含金量不明；
- **不区分性断言**：无论有无技能都过的断言（比如输出非空），虚增通过率。

skill-creator 的 mean±stddev 聚合证明这两类信号可程序化暴露，且与程序断言体系天然兼容（纯计算，不需要新模型调用）。

### 3.2 目标

- 评测结论从"过 N 例"升级为"过 N 例 ± 波动范围"，flaky 与不区分断言显式浮出；
- **不改判定语义**：单次判定逻辑、四类断言、execution/评分失败分离全部保持。

### 3.3 需求明细

| ID | 需求 | 必要 |
|---|---|---|
| R2-1 | 用例重复执行：eval_suite 支持每用例 repeats 配置（默认 1=现行为，推荐 3）；同一用例的候选组与基线组各自重复 | 是 |
| R2-2 | 逐例统计：每用例记录 passed 率、通过次数/总次数、结果是否一致（一致 / 翻转）；用例级结论聚合规则=多数决（票数相同算 failed，保守） | 是 |
| R2-3 | 组级统计：candidate/baseline 各自 pass_rate 均值 ± 标准差（跨用例），及 delta | 是 |
| R2-4 | 信号标注：`flaky`（该用例结果翻转）与 `non-discriminating`（candidate 与 baseline 该用例结论相同且都过）两种标注写入逐例结果 | 是 |
| R2-5 | 折算语义：eval:summary 的 passed 判定改用多数决结果；flaky 用例即使多数过也带标注进导出收据证据 | 是 |
| R2-6 | 成本可见：repeats>1 时模型调用量按倍数增长，进 budget 台账并在 UI 显示预估（排队前提示） | 是 |
| R2-7 | 跨迭代 delta：同 skill 的多个版本评测结果对比（版本 N vs N-1 的 pass_rate 变化），在版本列表可见 | 否（建议） |

### 3.4 验收标准

1. repeats=3 下，构造一个 1/3 概率失败的用例 → 标注 flaky，多数决结论正确；
2. 构造两条用例：一条有无技能都过、一条有技能才过 → 前者标 non-discriminating，后者不标；
3. repeats=1 时所有输出与现行为完全一致（回归零破坏，现有 214 测试不改断言即通过）；
4. budget 台账准确反映 repeats 倍数；UI 显示预估调用量；
5. 单元测试覆盖：多数决边界（1/3、2/3、平票）、stddev 计算、标注判定条件。

### 3.5 非目标

- 不做评测用例本身的自动生成/扩充（用例集仍由 build_eval_suite 从合同派生 + 用户可改）；
- 不做按 token/时长的成本方差（现有 usage 记账已够审计，方差分析只针对通过率）。

### 3.6 技术要点

- 数据模型：eval_case_result 增加 attempt 序号列（迁移脚本，注意 data/ 存量库兼容）；
- 聚合纯函数化（输入逐例 attempt 列表，输出统计）便于独立单测；
- repair-eval 复评时沿用同一 repeats 配置，保证新旧版本评测可比。

## 4. R3：盲评对照（P2）

### 4.1 动机

程序断言只能验证"格式/包含关系"，评价不了输出质量高低。v1.3 时以"无第二评审者"砍掉 P3-10，但 skill-creator 证明：**同一个模型以盲态**（不知道哪个来自 candidate、哪个来自 baseline）即可担任评审，不需要第二个人。此砍法判断有误，应修正。

### 4.2 目标

- 对照评测增加一维机器可读的质量结论："盲态下评审者更偏好哪组输出"，胜者归因入报告；
- 仍不阻塞导出（与 eval/trigger 同语义：如实标注）。

### 4.3 需求明细

| ID | 需求 | 必要 |
|---|---|---|
| R3-1 | 盲化：同用例的 candidate/baseline 输出匿名化（A/B 随机分配且随机序记录入库，可复验盲化正确性） | 是 |
| R3-2 | 盲评调用：评审提示含用例原题 + 两份匿名输出 + 评维度（正确性/完整性/格式纪律），要求输出结构化裁决（偏好 A/B/平手 + 归因文字）；**提示中不得出现任何可暴露来源的措辞** | 是 |
| R3-3 | 归因与防作弊：裁决的归因文字必须引用输出中的实际内容（抽查脚本验证引用存在），防评审凭位置/长度等伪线索裁决 | 是 |
| R3-4 | 汇总：盲评偏好分布（candidate 胜/平/baseline 胜），进 eval_run 结果与导出收据（新检查 `eval:blind`） | 是 |
| R3-5 | 评审者与生成者模型可配置分离（默认同模型——盲态即可接受；若用户配了第二模型则天然双盲） | 否（建议） |
| R3-6 | 平手语义：平手不算 candidate 优势；majority 平手 → eval:blind 结论 not_run（证据不足，不粉饰） | 否（建议） |

### 4.4 验收标准

1. 同一用例跑两次，A/B 分配不同 → 匿名化随机性可验证，归因一致；
2. 构造明显质量差（candidate 完整、baseline 缺半）→ 盲评正确偏好 candidate 且归因引用实际内容；
3. 两份输出完全相同 → 裁决为平手，汇总如实反映；
4. 盲评失败（模型返回不合 JSON）→ 该用例记评分失败，不拖垮整组（与现有评分失败分离语义一致）；
5. 单元测试覆盖：盲化随机性与可复验、归因引用抽查、平手汇总、失败隔离。

### 4.5 非目标

- 不追求"评审绝对公正"（同模型自评有已知偏差，盲态+归因引用是可承受的折中；文档需如实写明此局限）；
- 不做人机混合评审（skill-creator 的 HTML viewer 人工反馈环不在 skill-forge 无人值守目标内）。

### 4.6 技术要点

- 复用 agent_run 体系：盲评即一类新 case（kind=blind_compare）；
- 盲化记录（哪个是真 candidate）只入库不进提示；审计时可还原；
- 成本：每用例 +1 次模型调用，进 budget 台账（并入 eval stage 记账）。

## 5. 总体优先级与依赖

| 项 | 优先级 | 依赖 | 预估规模 | 交付物 |
|---|---|---|---|---|
| R1 触发优化 | P1 | 无（eval_run 框架已就绪） | 最大：新维度 + 生成器 + 迭代器 + 冻结语义（description 变更→新版本） | 第六维 trigger + 迭代优化闭环 |
| R2 方差分析 | P2 | 无（纯计算层） | 中：DB 迁移 + 聚合层 + 回归 | repeats/flaky/non-discriminating + 组级统计 |
| R3 盲评对照 | P2 | 无 | 中：盲化 + 新 case 类型 + 汇总 | eval:blind 检查 + 偏好分布 |

实施顺序建议：**R2 → R1 → R3**（R2 最小且先行可为 R1/R3 提供更可信的统计底座；R1 价值最高但改动面最大，放在统计层稳定后动）。

## 6. 全局验收底线（三项共用）

1. **诚实纪律不破**：所有新维度未运行/证据不足 → not_run，不阻塞导出，不回写冻结版本行；
2. **回归零破坏**：现有 214 项测试不修改断言全部通过；新增功能各配专项测试（对齐 v1.3 的 test_repair_loop / test_repair_eval_loop 模式）；
3. **预算全记账**：新增模型调用一律进 budget 台账（stage_id 区分），预留+实际双写；
4. **磁盘字节唯一真相**：trigger 用例集、盲化分配记录等新状态全部落盘/入库，进程重启可恢复；
5. **导出对账**：新维度结论在导出收据与数据库间一致，篡改检测（409）覆盖新文件。
