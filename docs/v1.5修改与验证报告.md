# v1.5 修改与验证报告：token 消耗优化（M1–M5）

> 基线：v1.4（commit a4ae9d5），233 项后端测试全绿。
> 依据：97 次真实运行 token 消耗分析（13.49M tokens，其中 50 次
> budget_exceeded 运行平均踱到 216k 才止损、占总消耗约 80%；根因是
> 全量历史逐轮重发的二次方增长 + read_file 工具输出均值 7.5k 字符/次）。
> 参考 skill-creator 的做法：成本可见（benchmark 表列 tokens）、
> 便宜模型干裁判活、工具输出不进长历史。

## 修改清单

### M1：套件预算字段消费（死字段激活）

`build_eval_suite` 一直把 `budget: {max_tokens_per_case, max_tokens_total}`
写进套件用例，但 `eval_run` 处理器从不读——执行侧实际用 200k/40 默认。

- `app/generation/evaluation.py`：常量 4k/60k → 80k/200k（此前从未生效）；
- `app/workers/handlers/eval_run.py`：逐例优先级 = API 显式传参 > 用例/套件
  声明预算 > 处理器默认；套件整体封顶——累计达 `max_tokens_total` 后
  余例记 skipped（score_error 注明"封顶"），不假装跑过；
  `meta_json.budget` 记录声明上限、实际累计、封顶触发。

### M2：执行预算默认收紧

`app/workers/handlers/agent_run.py`：默认 200k/40 轮 → 80k/15 轮。
依据：completed 运行平均 62k / 中位 22 步；新默认覆盖成功路径，撞墙
运行在约 1/3 成本处止损。需要长任务时 runs/evals API 显式传参不受影响。

### M4：成本入收据（对齐 skill-creator 的 benchmark 可见性）

- `app/generation/evaluation.py`：`_eval_cost()` 聚合本次评测关联
  AgentRun 的 prompt+completion tokens，按 candidate/baseline 分组；
  `eval:summary` 证据追加"成本：本次评测消耗 X tokens（candidate Y、
  baseline Z）"——"贵不贵"与"好不好"同屏可见；
- `app/workers/handlers/eval_run.py`：运行视图新增 `cost` 段（三分量）。

### M3A：工具输出历史截断降档 + read_file 分页

- `app/tools/registry.py`：`MAX_TOOL_OUTPUT_CHARS` 20k → 4k；截断提示
  带分页指引。`read_file` 新增 `offset`（1 起始行号）/`limit`（行数）
  参数，输出带 `[行 a-b / 共 n 行]` 头；越界/非法入参返回 JSON 错误
  （不假装有内容）。工具输出随轮次全部重发进上下文，是 token 膨胀
  主因，降档直接压缩历史底盘；
- `app/executors/api_executor.py`：库默认轮次 40 → 15（与 M2 对齐；
  生产路径均显式传参）。

### M5：分级模型环境变量

`app/llm/openai_compat.py` 新增 `judge_provider_from_env()`：裁判类调用
（盲评评审 `eval_run.judge_provider_factory`、触发验证
`trigger_run.provider_factory`）优先读 `SKILLFORGE_JUDGE_LLM_BASE_URL` /
`_MODEL` / `_API_KEY`；URL 与 MODEL 必须同时配置才生效，否则整体回落
主模型（不做半套配置拼接）。v1.4 发布文档中标注的"未来可选增强"落地。

### M3B：执行器历史窗口化（旧轮工具输出降档）

`app/executors/api_executor.py`：每轮模型调用前，把窗口外
（`history_tool_keep_rounds` 轮之前，默认 3）且超 600 字符的旧 tool
消息 content 原地降档为头尾各 200 字符的摘要，带“原始 N 字符 +
read_file offset/limit 分段重读”指引；tool_call_id 配对不变，幂等不
叠加，`keep_rounds=0` 关闭。完整内容仍在 StepRecord 与沙箱磁盘。
`ExecutorResult.history_window`（keep_rounds / compressed_messages /
saved_chars）经 agent_run 并入 budget_json 落库，无新迁移。历史重发
的二次方增长被压成近线性。

## 行为兼容性说明

- 未配 `budget` 的套件、未显式传参的 API 调用：行为 = 新默认
  （80k/15 轮），旧数据不受影响；
- 未配 `SKILLFORGE_JUDGE_LLM_*`：裁判调用与主模型同源，行为同 v1.4；
- read_file 无 offset/limit 调用：小文件（≤4k）行为不变，大文件截断
  点前移且提示可分页；
- M3B 窗口化默认开启（keep=3 轮）：仅影响发送给模型的旧轮工具输出
  摘要化，StepRecord/沙箱/评测断言基于最终产出，不受影响；短输出
  （≤600 字符）与近 3 轮输出逐字保留；需要旧行为可传
  `history_tool_keep_rounds=0`。
