## 真实宿主使用反馈（2026-10-04 首次实验）

按上述计划把 smoke 产物 `meeting-action-extractor` 装入 CatPaw
（`install-skill.ps1` 正常完成：dry-run 预览 → 全新安装 → 提示 candidate
状态），然后用一段真实风格的会议纪要实测脚本链路。**一次实验抓到三个
此前任何测试与检查器都抓不到的问题**：

1. **跨脚本契约不一致（集成级缺陷，确定性复现）**：
   `extract_actions.py` 输出键为 `"actions"`，`format_table.py` 只认
   `("action_items", "items", "行动项", "data")`——同一生成流程产出的
   两个脚本互不兼容，管道直接报错退出。对照实验证实每个脚本单独都正确
   （裸数组输入 format_table 正常出表）。结论：静态检查（ast.parse /
   file_hash / no_secrets）和 execution smoke（空输入退出码）都看不到
   这类缺陷，**只有端到端管道评测能抓到——P1-2（评测阶段接入主链）
   的存在意义由此从"推断"变成"实证"**。
2. **输出本地化不一致**：`extract_actions.py` 同时产出 `status`
   （"unknown"）与 `status_label`（"未知"）两个字段，但 `format_table.py`
   用了前者——表格里中文负责人列"未提供"是本地化的、状态列却冒出英文
   raw 值。同一产物内部呈现标准不统一。
3. **提取召回率偏低**：样例纪要 5 个行动项只抓到 1 个（漏掉"下周一前"
   "本周五之前""明天前"三种期限表述；"XX负责Y"句式中 owner 也未识别）。
   正则启发式实现的功能上限。说明生成阶段的模型需要更强的"样例驱动"
   约束（给正/负例要求脚本处理），或者接受这是 v1 的能力边界并如实标注。

**对砍项决策的影响**：P1-2 的触发条件（"等真实使用反馈再评估"）现已
满足一部分——已证实存在只有评测阶段能抓的缺陷类别。是否现在接入，
取决于产出物要不要交给别人用：自用且能接受人工过一遍，可继续推迟；
要宣称"生成即可用"，P1-2 应从推迟队列取出。

**安装侧反馈（正面）**：安装脚本 dry-run/安装/提示 candidate 全链路
符合预期；ZIP 内 delivery/ 五个 JSON 原样保留，审计可追溯性成立；
手动 no_secrets 扫描零命中。

- **评测抓到的真实缺陷**（自动化版的"CatPaw 实验"，无需人工装包）：

## P1-1：补齐 4 个未注册检查器

**问题**：`engineering/profiles/default.yaml` 声明 8 个 checker，实现只注册
4 个。`validation:resource_reference`、`validation:file_hash`、
`validation:no_secrets`、`coverage:requirements` 运行时全部 NOT_RUN。

**证据**：真实 smoke 收据 notes 明细；`validation.py` 的 `_CHECKER_MAP`
注册清单 vs profile 声明清单。

**影响**：任何真实流程在当前系统下**结构性无法达到 DELIVERED**——收据
永远 candidate。"如实报告能力边界"不能替代能力本身。

**修复方案**（按价值排序）：
1. `validation:no_secrets`：最优先。复用 `delivery.py` 打包侧已有的
   `_scan_for_secrets` 与 `SENSITIVE_*` 常量，抽成公共模块，validation
   阶段对每个候选文件调用——同时消除"打包侧扫密钥、验证侧不扫"的双体系。
2. `validation:file_hash`：manifest 已含 sha256，逐文件实测磁盘哈希比对。
3. `validation:resource_reference`：解析 SKILL.md / references 引用路径，
   检查被引文件存在于 manifest。
4. `coverage:requirements`：`coverage.py` 的 `evaluate_coverage` 已实现，
   只是把它的输出注册成 `coverage:requirements` 单一聚合 check
   （现在输出为逐需求 `coverage:{rid}`，聚合视图单独生成）。

**验收标准**：真实模型 smoke 的收据中上述 4 项不再是
"检查器未注册"型 NOT_RUN；在静态/覆盖证据齐全的用例中可达 DELIVERED。

## P1-2：评测与修复回路接入生成链

**问题**：`app/generation/evaluation.py`（T14 对照评测）与
`app/generation/repair.py`（T15 有界修复）在 `app/` 内**零调用**。
生成链 handler 只执行 extract→plan→generate→validate→coverage→freeze。

**证据**：`grep -rn "import evaluation|import repair" app/` 除模块自身
无结果；smoke 全链路 worker 仅执行 3 个 job，无 eval/repair 阶段。

**影响**：与 A1（宿主适配器孤岛）同病——按计划实现并通过测试，但从未
被主链触发。修复回路（证据驱动的有界自动修复）是 v1 设计的核心卖点，
当前实际不参与任何生成。

**修复方案**：在 `generation_stage` handler 的 validate 之后、freeze 之前
插入两个阶段：`evaluate`（调用 `evaluate_candidate` 建测试集跑对照）→
`repair`（失败证据非空且修复轮次 < 预算时调用 `repair.py`，每轮有证据
改善才继续）。预算 ledger 的 `eval` / `repair-N` 键已预留，直接使用。
同时把 `FlowState.EVALUATING / REPAIRING` 状态真实流转起来（目前是死状态）。

**验收标准**：e2e 中构造一个"首版验证失败"的剧本，断言：评测阶段产生
对照记录；修复阶段最多 N 轮且每轮 evidence 改善；修复失败时流程 failed
而非 delivered；预算含 eval/repair 记账。

## P1-3：execution 维度生产者

**问题**：`DeliveryReceipt` 五维中的 execution 维度，`app/generation/`
内没有任何模块产生 `execution:` 前缀的 check——维度永远 None。

**证据**：`grep -rn "execution:" app/generation/` 零结果；smoke 收据
`execution=None`。

**修复方案**：最小实现放在 `runtime.py`（T13 已有工具预检）：对候选的
脚本文件做真实执行 smoke（空输入调用，断言退出码 0 / 非崩溃），产出
`execution:script:{path}` checks。完整实现可依赖 P1-2 的评测阶段输出
`execution:case:{id}`。注意执行安全边界：仅限项目 data 目录内、超时上限、
无网络——与现有沙箱声明一致。

**验收标准**：五维收据中 execution 不再是 None；脚本崩溃时如实 FAILED
并阻断 DELIVERED。

## P1-4：CI

**问题**：无 .github/workflows，208 个测试的回归保障全靠手工。

**修复方案**：单 workflow：push/PR 触发 → uv sync → pytest →
frontend `npm ci && npx tsc --noEmit && npx vitest run && npm run build`。
注意 npmmirror registry 与 `SKILLFORGE_TOKEN` 测试值的 secrets 不需要
（测试自带）。约 40 行 YAML。

**验收标准**：push 后 GitHub Actions 全绿徽章可挂 README。

## P2-5：宿主验证自动化

**问题**：CodexAdapter 读 `~/.codex/skill-verification/records.json`，
该文件靠人工编写——验证"宿主真实触发"的闭环缺自动驱动，且项目至今
没有一次 host=passed 的正向证据（只在单测里 mock 过）。

**修复方案**：新增 `app/platforms/driver.py`：给定用例集与技能目录，
通过 codex CLI 批量发送正/负触发提示词，自动捕获结果写 records.json，
再调 validate_delivery。驱动器本身产出 source=codex-cli 的原生记录。
人机边界保留：驱动前打印将执行的用例清单，`--yes` 确认后执行。

**验收标准**：一台装有 codex CLI 的环境跑通完整闭环，收据
host=passed 的截图/日志入档；API 注入用例在驱动器下不可复现。

## P2-6：安装器（T21 子项提前）

**问题**：导出的 ZIP 没有落地安装能力：无路径冲突预览、无备份、无
原子替换、无回退。交付物"最后一公里"缺失。

**修复方案**：按 T21 计划实现 `app/platforms/installation.py`：
`prepare_install(receipt, target)` 生成冲突预览（dry-run，列出将写
入/覆盖的文件）；`install_delivery(plan, authorization)` 仅在显式授权
后执行——备份已有技能 → 临时目录写入 → 原子 rename → 失败回退。
测试覆盖：未授权不写盘、已有内容不静默覆盖、中途失败可回退。

**验收标准**：真实安装一个 smoke 产物到隔离目录，覆盖/回退/拒绝三条
路径各有测试。
